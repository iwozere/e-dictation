# e-dictation — Product & Architecture Review

> **Date:** 2026-06-24
> **Reviewers:** Senior Product Owner (Part 1) · Senior Application Architect (Part 2)
> **Scope:** Full application scan — Flutter client, Supabase schema/RLS, Edge Functions (`on_dictation_save`, `ocr_image`), player engine, attempts/scoring, auth.

## How to read this document

- **Part 1** is written from the product owner's chair: what users feel, what's missing, what would move the needle. It does not assume knowledge of the code.

# Part 1 — Product Owner Review

## 1.1 What the product does well today

Before improvements, it's worth recording the strengths, because several are genuinely differentiating and must not be regressed:

- **The sentence-playlist player is the right architecture.** Step-through with a configurable inter-sentence pause and a 1-second "get ready" lead-in is exactly the exam-simulation feel the spec promised. The pause-between-sentences logic is the killer feature and it works.
- **Frictionless student entry.** Share code → anonymous session → optional name + PIN → straight into dictation. No signup wall. This is the correct call for the teacher/homework market.
- **Typing + immediate per-sentence diff** (word-level LCS highlighting) already delivers a Phase-3-grade feedback experience. Students see exactly which words were wrong/missing.
- **OCR import** (photograph a textbook page → text) is a delightful, unplanned shortcut for teachers and a real time-saver.
- **TTS status surfaced** (`pending/processing/done/error`) means the UI can show honest progress instead of spinning forever.

## 1.2 High-priority product gaps

### P1 — Scoring ignores the two things German dictation is *about* (capitalization & punctuation) — **Impact: High, Effort: M**

The whole pitch (spec §1.2, §3.5) is that German dictation rewards correct **noun capitalization, umlauts, ß, and punctuation**. But the current correctness check lowercases the text, strips all punctuation, and converts `ß → ss` before comparing. Consequences a teacher will immediately notice:

- "der hund" scores **correct** against "Der Hund." — capitalization error invisible.
- "Strasse" scores **correct** against "Straße" — the ß/ss distinction (a classic German test point) is erased.
- Missing or wrong commas/periods never count.

This is the single biggest credibility risk: a dictation tool that doesn't catch dictation mistakes. We need a **scoring mode** that grades on exact orthography (with a clear, itemized breakdown: "2 capitalization, 1 umlaut, 1 punctuation"), while optionally offering a lenient mode for younger learners.

### P2 — Results a teacher can't trust — **Impact: High, Effort: M**

Scores are computed on the student's device and sent to the server as a number. There is nothing stopping a student (or a bored one with dev tools) from submitting a 100%. For a product whose *first paid feature* is the progress dashboard (spec §7.1), trustworthy numbers are the product. We must score authoritatively on the server.

### P3 — No Google sign-in; no student account upgrade — **Impact: Med, Effort: M**

Spec Phase 1 lists "email + Google OAuth." Only email + anonymous exist. Teachers expect one-tap Google in this market (school Google Workspace is ubiquitous). Separately, the anonymous→named-account upgrade path (spec §3, Phase 2) isn't built, so a student's history is tied to a name+PIN typed into one browser's local storage — lose the device, lose the history.

### P4 — Class/group workflow is half-present — **Impact: Med, Effort: M**

Classes exist as an entity and a tab, dictations can carry a `class_id`, but there is no student-facing "join a class" or per-class assignment/roster flow, and no per-class results rollup that a teacher would actually use for grading. This is the monetization centerpiece (spec §7.1 "first paid feature") and needs an end-to-end story.

## 1.3 Quick wins (high value, low effort)

- **QW1 — "Retry TTS" button.** When `tts_status = error`, the teacher currently has no in-app recovery. Add a one-tap retry on the dictation detail card. *(S / Med)*
- **QW2 — Copy-link & QR for sharing.** A 6-char code is good; a QR code projected on the classroom wall is better for handing a dictation to 30 phones at once. *(S / High)*
- **QW3 — Surface save failures to the student.** Attempt saving is fire-and-forget; if it fails the student still sees their score but the teacher never sees the attempt. Show a retry toast on failure. *(S / Med)*
- **QW4 — Replay-count / "listen again" affordance in listen-only mode.** Students doing real dictation need an obvious "repeat this sentence" that doesn't reveal text. The engine supports `repeatCurrent()`; expose it prominently. *(S / Med)*
- **QW5 — German UI localization.** The audience is German teachers but the UI is English-only ("Score", "Sentence", "Before you start"). At least ship a German locale. *(M / High for the target market)*
- **QW6 — Word/character count + estimated audio length** shown live in the create screen, with the 500-word limit as a friendly progress bar rather than a hard error at save. *(S / Med)*

## 1.4 Feature opportunities (roadmap-aligned)

- **AI mistake categorization (Phase 3 proper).** Once server-side scoring exists, layer Claude-based categorization ("3 capitalization, 2 umlaut") and a class-level "most common mistakes" view. This is the €14/mo tier.
- **Teacher voice input (Whisper, Phase 2).** Not yet present; high teacher appeal ("just read it aloud").
- **Adaptive re-dictation** from a student's recurring errors.
- **PDF export of results** for parent's evenings / grade books.
- **Assignment due-dates & "who hasn't done it yet"** — the nagging tool teachers actually want.

## 1.5 UX polish backlog

- Speed/pause selectors are tiny `GestureDetector` chips — below the 44px accessible tap target and not keyboard-focusable.
- No dark-mode review of the diff colors (warning/error on tinted backgrounds may fail contrast).
- The identity panel buries "See my past results"; returning students should land there faster.
- No empty-state guidance on the teacher dashboard for a brand-new account.
- No confirmation/undo on dictation delete.

# Part 2 — Application Architect Review

## 2.0 Verdict

The codebase is **well above average for an MVP**: clean feature-first layout, disciplined repository pattern with `(value, Failure)` result tuples, an RLS hardening migration that shows real security awareness (002), and a genuinely careful player state machine. The problems below are the normal cost of speed, not signs of a troubled codebase. Two of them (server-side scoring, the splitting/caching spec drift) are worth fixing before the dashboard is sold.

## 2.1 Assessment of the PO's proposals

| PO item | Architect verdict | Notes |
|---|---|---|
| **P1** Orthography-aware scoring | **Endorse, do with P2** | Don't build it twice client-side. Make scoring a single pure function shared by client preview and server authority. See 2.3. |
| **P2** Server-side authoritative scoring | **Endorse — highest-leverage fix** | The expected text already lives server-side; the student need only submit answers. Removes the client-trust hole *and* the duplicated logic. See 2.4-S1. |
| **P3** Google OAuth + account upgrade | **Endorse, low risk** | Supabase supports both natively (`signInWithOAuth`, `linkIdentity`/`updateUser` to upgrade an anonymous user). Mostly client work. |
| **P4** Class workflow | **Endorse, schema is ready** | `class_id` and `classes` already exist (good Phase-1 decision). Needs a join-roster table and RLS; no painful migration. |
| **QW1** Retry TTS | **Easy** | Just re-invoke `on_dictation_save`; already idempotent (deletes old sentences first). |
| **QW2** QR/copy | **Trivial** | Pure client. |
| **QW3** Surface save failure | **Easy + correctness fix** | Current fire-and-forget also swallows the `Future`; see 2.5-C4. |
| **QW4** Repeat affordance | **Trivial** | `repeatCurrent()` exists. |
| **QW5** i18n | **Medium, do early** | Retrofitting `intl`/ARB after dozens of screens is costly; the longer we wait the worse it gets. `intl` is already a dependency. |
| **QW6** Live counts | **Trivial** | Client-only. |

## 2.2 Spec/implementation drift (documentation debt) — **Impact: Med**

The shipped system diverges from `CLAUDE.md` and `docs/project-specification.md` in ways that will mislead the next engineer (and already contradict the repo's own "critical constraints"):

1. **Sentence splitting is regex, not Claude.** `on_dictation_save` calls a local `splitIntoSentences()`; there is no `ANTHROPIC_API_KEY` usage anywhere. The regex is actually decent (abbreviation protection, German cases) and avoids an API cost/latency — a reasonable engineering call — **but** the spec, CLAUDE.md, and the function's own header comment all still claim Claude. **Recommendation:** either document the regex approach as the intentional Phase-1 choice or wire Claude behind a feature flag. Update CLAUDE.md §"TTS is pre-generated" and the file header either way.
2. **`flutter_cache_manager` is a dependency but never used.** Offline MP3 caching is listed as a *critical constraint* ("all sentence MP3s must be cached"). Today `just_audio` streams the public URL every play; no offline support, and repeat playback re-downloads. **Recommendation:** wrap audio sources in a `LockCachingAudioSource` or resolve URLs through the cache manager. (Note: caching on Flutter Web is limited — scope this honestly per-platform.)
3. **`audio_session` is a dependency but never configured.** Another critical constraint ("configure AVAudioSession before any playback; test Safari/iOS early"). Without it, iOS/Safari will likely have playback bugs (silent-switch, interruptions, autoplay). **Recommendation:** configure `AudioSession.instance` with a speech configuration in `main()` before first playback. This is a latent Phase-1 risk that only shows up on real devices.

These three are grouped because they share a root cause: the docs assert invariants the code doesn't yet honor. Pick truth-in-docs or build-to-spec, but close the gap.

## 2.3 Security findings

### S1 — Client-submitted scores are trusted (already raised as P2) — **Severity: High**
`attempts.score`, `score_correct`, and `score_total` are computed in `player_screen.dart`/`student_results_view.dart` and inserted directly. RLS (`attempts: insert own`) only checks `auth.uid() = student_id` — not that the values are honest or that the student even played the dictation. Any client can POST a perfect score. **Fix:** move scoring into a `SECURITY DEFINER` RPC (`submit_attempt(dictation_id, answers)`) that loads the canonical sentences, scores server-side, and writes the row. Client sends answers only.

### S2 — Student history is brute-forceable; PII/answer leak — **Severity: High**
`get_student_attempts(p_name, p_pin_hash)` gates on name + an **unsalted SHA-256 of a 4-digit PIN**. The PIN space is 10,000 and the function accepts the *hash*, so an attacker who knows/guesses a classmate's name precomputes all 10,000 hashes and calls the RPC up to 10,000 times to retrieve that student's full answer history. There is no rate limiting and names are inherently guessable. The code comment acknowledges the PIN is "trivially reversible" but still uses it as the sole access gate. **Fixes (layered):**
- Rate-limit the RPC (per-IP / per-session attempt counter, e.g. a `pin_attempts` table or Supabase edge rate limit).
- Accept the *raw* PIN in the RPC over TLS and hash server-side with a per-row salt, so precomputation doesn't help.
- Consider a longer/alphanumeric PIN, or better, push returning students toward a real (Google) account for durable, secure history (ties to P3).

### S3 — Attempt impersonation & spam — **Severity: Med**
Any anonymous session can insert an attempt for **any** `dictation_id` with **any** `student_name`. A student can submit results as "classmate" or flood a teacher's dashboard. The server-side `submit_attempt` RPC (S1) should also (a) verify the dictation exists/has a share code and (b) ideally bind the attempt to the actual anonymous `auth.uid()` so duplicates/floods are attributable.

### S4 — Share-code entropy & enumeration — **Severity: Med**
Codes are 6 chars drawn from **hex only** (`gen_random_uuid()` → `0-9A-F`), i.e. 16⁶ ≈ 16.7M, not the 36⁶ ≈ 2.2B implied by "6-char alphanumeric." `get_dictation_by_share_code` is unauthenticated-friendly (granted to `anon`) and unthrottled, so the keyspace is scrapeable over time — leaking dictation titles, full text, and sentences. **Fix:** generate from a full alphanumeric alphabet (exclude ambiguous chars like O/0/I/1 for UX), and rate-limit the RPC.

### S5 — Edge Function input limits / cost abuse — **Severity: Med**
- `ocr_image` accepts an unbounded `image_base64` and forwards to Cloud Vision with no size cap and no per-user throttle → memory/cost DoS. **Add a payload size limit and rate limit.**
- `on_dictation_save` has the good 500-word guard, but nothing throttles *how often* a teacher can trigger regeneration (every text edit re-runs full TTS). A malicious or buggy client could loop edits and run up Google TTS cost. **Add a per-dictation regeneration cooldown / debounce.**

### S6 — Minor hardening
- `getCallerUserId` decodes the JWT payload without signature verification, relying entirely on Supabase's gateway `verify_jwt`. That's acceptable *given* `verify_jwt = true` in `config.toml` — worth a comment-anchored assertion and a config test so the assumption can't silently regress.
- CORS `Access-Control-Allow-Origin: *` on functions is fine for public reads but combine with the rate limits above.

## 2.4 Performance findings

### Pf1 — Sequential TTS generation risks Edge Function timeout — **Impact: High at scale**
`on_dictation_save` loops sentences with `await generateTts → upload → insert` **serially**. A 500-word dictation can be 30-40 sentences; at network latency per Google call this can approach or exceed the Edge Function wall-clock limit, leaving a half-generated dictation. **Fix:** generate/upload with bounded concurrency (e.g. `Promise.all` in batches of 4-5), and/or process in a queue with resumability. Also make the function safely re-runnable from any partial state (it already deletes-then-inserts, so a clean retry works — but a mid-run timeout leaves orphaned rows; consider upsert-by-position).

### Pf2 — Inaccurate duration estimate — **Impact: Low (correctness)**
`durationMs` is estimated from byte length (`bytes/16000`). Real bitrate varies; this drives any UI progress. Prefer requesting timing from the TTS response or parsing the MP3 header; at minimum document it as approximate.

### Pf3 — Dashboard over-fetch — **Impact: Med as libraries grow**
`fetchDictations` pulls **every sentence row (text + audio_url)** for **every dictation** just to render cards. A teacher with 100 dictations × 30 sentences downloads thousands of rows for a list view. **Fix:** the card needs only a sentence *count* and `tts_status`; fetch full sentences lazily on the detail/player screen. Add a `count` or a lightweight view.

### Pf4 — No pagination — **Impact: Med**
`listAllAttempts` and the dictation list have no limit/paging. A busy class generates hundreds of attempts; the Results tab will degrade. Add range-based pagination.

## 2.5 Code quality / maintainability

### C1 — Scoring & normalization logic duplicated — **Impact: Med**
`_normalize` and the score computation exist in **both** `player_screen.dart` and `student_results_view.dart`, computing the same number independently (player saves it; view recomputes it for display). They can silently diverge. **Fix:** extract a single `scoring.dart` pure module (`Score score(List<Sentence>, Map<int,String>)` + `normalize`), used by the view and — once S1 lands — mirrored by the server RPC. This is the natural home for the P1 orthography rules too.

### C2 — Near-empty test suite — **Impact: Med (rising)**
Only the default `widget_test.dart` exists. The two most logic-dense, regression-prone areas — `splitIntoSentences` (lots of edge cases) and the player state machine (`PlaybackNotifier`, with its subtle paused/pauseBetween/completed transitions) — have zero tests. **Fix:** unit-test `splitIntoSentences` (abbreviations, decimals, blank lines, quotes) and the diff/scoring function first; add a notifier test for the pause/resume edge cases the comments describe.

### C3 — Magic strings — **Impact: Low**
SharedPreferences keys (`'student_name'`, `'student_pin_hash'`) and RPC names are inline string literals across files. Centralize as constants.

### C4 — Swallowed async in attempt save — **Impact: Med (correctness)**
`_saveAttempt` is fire-and-forget and `_savingAttempt` is set true but never reset, so a failed save is invisible and can't be retried (ties to QW3/S3). Once scoring moves server-side, await the RPC and reflect success/failure in the results UI.

### C5 — `currentUser` role from JWT metadata can be stale — **Impact: Low**
`AuthRepository.currentUser` reads `role` from `raw_user_meta_data`; the doc comment already flags it as a lesser path. Ensure no security decision keys off it (RLS uses `auth.uid()`, so this is presentational only — keep it that way).

## 2.6 Recommended sequencing

1. **Foundation fix (1 sprint):** Server-side `submit_attempt` RPC (S1+S3) → extract shared `scoring.dart` (C1) → add orthography scoring mode (P1). One coherent change that closes the biggest security hole, kills the duplication, and delivers the headline product fix.
2. **Security hardening (parallel, small):** Rate-limit + salt the history RPC (S2), widen share-code alphabet + throttle (S4), cap OCR payload + TTS regeneration cooldown (S5).
3. **Spec-truth (small):** Configure `audio_session`, wire `flutter_cache_manager`, and reconcile the splitting docs (2.2) — close the Phase-1 "critical constraint" gaps before any iOS launch.
4. **Reliability (medium):** Concurrent TTS generation with resumable partial state (Pf1); dashboard over-fetch + pagination (Pf3/Pf4).
5. **Growth:** Google OAuth + account upgrade (P3), end-to-end class workflow (P4), then AI categorization/Whisper per roadmap.
6. **Always-on:** Backfill tests for splitting + scoring + player (C2); ship German localization (QW5) before it's expensive.

# Part 3 — Security Engineer / Penetration Test Review

> **Lens:** adversarial. Assume a motivated student with browser dev tools, a curious competitor, and an automated scraper. The architect pass (2.3) flagged the issues structurally; this pass walks the actual attack paths and adds a threat model.

## 3.1 Threat model (who attacks what)

| Actor | Capability | Prize |
|---|---|---|
| Bored/competitive student | Anonymous session, dev tools, can read all client JS | Fake a perfect score; read classmates' answers; impersonate |
| Returning-student impersonator | Knows classmates' first names | Pull another child's full history |
| Competitor / scraper | Anonymous JWTs at scale, no rate limit | Harvest every teacher's dictation text + audio |
| Cost attacker | One free teacher account | Run up Google TTS / Vision bills |

The trust boundary is the **client**, and right now too much authority lives on the wrong side of it.

## 3.2 Walkthroughs of the live attack paths

### A1 — Forge a perfect score *(confirms S1, Severity: High)*
The score is computed in `player_screen._saveAttempt` and POSTed as `score`/`score_correct`/`score_total`. The only RLS gate is `auth.uid() = student_id`. Attack: open network tab, replay the `attempts` insert with `score:100`, or just call `supabase.from('attempts').insert(...)` from the console of the anonymous session. There is no server check that the answers match the score, or that any audio was ever played. **The dashboard is forgeable by design.** Fix is S1's `submit_attempt` RPC (answers in, score computed server-side).

### A2 — Enumerate a classmate's history *(confirms S2, Severity: High)*
`get_student_attempts(p_name, p_pin_hash)` is granted to `anon` and takes the **hash**, not the PIN. Exploit, fully scripted:
1. Pick a target's name (often shown elsewhere, or just try class rosters).
2. Precompute `sha256("0000")…sha256("9999")` — 10,000 hashes, milliseconds.
3. Loop the RPC with each hash until rows return.
No throttle, no lockout. Worst case 10,000 calls returns the child's full answer text and scores. Even simpler: many students will set no PIN, and `student_pin_hash` is then `null` — confirm whether a `null` hash collapses the gate (the SQL requires `p_pin_hash is not null`, so name-only is blocked, good — but the 4-digit space is the real hole). **Layered fix:** server-side salted hash of the raw PIN + per-session/IP attempt counter + push to real accounts for durable history.

### A3 — Impersonate / flood *(confirms S3, Severity: Med)*
Nothing binds `student_name` to the session. A student submits attempts as "Anna Müller" for any `dictation_id`, poisoning the teacher's grade data or burying it under spam rows. Fix: `submit_attempt` binds to `auth.uid()` and validates the dictation.

### A4 — Scrape the whole catalog *(confirms S4, Severity: Med)*
`get_dictation_by_share_code` is callable by `anon` with no rate limit, and codes are **hex-only 6-char** (16.7M space, not the 2.2B alphanumeric implied). A scraper with rotating anonymous JWTs can sweep the keyspace and exfiltrate every dictation's title, full text, and sentences — i.e. teachers' (potentially copyrighted) content. Fix: widen alphabet **and** rate-limit the RPC; consider returning a generic error + small random delay to slow probing.

### A5 — Burn the budget *(confirms S5, Severity: Med)*
- `ocr_image` forwards an unbounded base64 image to Cloud Vision. A loop of large images = uncapped Vision spend and function memory pressure. Add a hard payload cap (e.g. ≤5 MB) and a per-user rate limit.
- `on_dictation_save` re-runs **full TTS on every text edit**. Scripted edit-loop = uncapped Google TTS spend. Add a per-dictation regeneration cooldown and/or a daily generation quota per account.

## 3.3 Additional security observations (new, not in 2.3)

- **S7 — Public storage bucket is fully world-readable.** `dictations` bucket is `public = true` with `select` to everyone. Audio URLs are unguessable (UUID path) so it's low risk *today*, but combined with A4 (scraping codes → you get the dictation row → not the audio path directly, but the sentence rows carry `audio_url`). Net: catalog scraping also yields playable audio. Consider signed URLs for non-public dictations if "private to a class" is ever a feature.
- **S8 — No audit trail.** There is no log of who accessed what dictation/attempt. For a children's-data product, an access log is both a security and a compliance asset (see Part 4).
- **S9 — Anonymous session lifecycle.** Anonymous users accumulate in `auth.users` indefinitely; each can insert attempts. No cleanup job. Minor abuse-surface and data-bloat vector.
- **S10 — Secrets posture is good** — keys are Edge-Function-only, client uses `--dart-define`, `.env.local` git-ignored. Keep it. Add a check that `verify_jwt = true` can't regress (tie to S6).

## 3.4 Security priorities
1. `submit_attempt` server-side RPC (A1, A3) — closes the two integrity holes at once.
2. Rate-limit + salt the history RPC (A2) — highest *confidentiality* risk for minors' data.
3. Widen + throttle share codes (A4); cap OCR + TTS regeneration (A5).
4. Then S7–S9 hardening as the product adds private/class content.

# Part 4 — Privacy / Data-Protection (GDPR) Review

> **Lens:** This is a product that processes **children's personal data** in the EU (spec targets German schools; deployment is `eu-central-1`). That triggers GDPR including the heightened protections for minors (Art. 8). Nobody currently owns this risk class, and it is the kind that produces regulatory and reputational damage disproportionate to the engineering effort to fix it.
>
> *Not legal advice — flag for counsel. But these are the obvious exposures an engineer can see.*

## 4.1 What personal data is processed today

| Data | Where | Sensitivity |
|---|---|---|
| Student first name (free text) | `attempts.student_name`, SharedPreferences | PII of a minor |
| Student answers (their writing) | `attempts.answers` (jsonb), plaintext | PII; reveals ability/performance |
| Scores / performance over time | `attempts.score*`, `completed_at`, `started_at` | Profiling of a minor |
| 4-digit PIN (hashed, unsalted) | `attempts.student_pin_hash` | Weak credential |
| Teacher email, display name, role | `profiles`, `auth.users` | Standard PII |
| Teacher content (dictation text) | `dictations.full_text` | Possibly copyrighted (spec §8) |

## 4.2 Findings

### G1 — No lawful basis / consent flow for minors — **Severity: High**
A child types their name and starts a dictation; their name, written answers, and performance are stored and shown to a teacher, with **no consent step, no privacy notice, and no age handling**. Under GDPR (and German BDSG / school-data rules), processing children's data needs a clear lawful basis — typically the school as controller with parental consent, *not* the child clicking "Start." **Recommendation:** define the controller/processor relationship (the **school/teacher is controller, e-dictation is processor**), ship a Data Processing Agreement, and design the entry flow so consent is captured by the teacher/school, not the child. Make the name truly optional with an explicit "your teacher will see this" notice (the copy exists; the legal framing doesn't).

### G2 — No data-subject rights mechanism — **Severity: High**
There is no way to **export** or **delete** a student's data (Art. 15/17), and for anonymous students it isn't even findable (no stable ID). A parent asking "delete my child's data" cannot be served. **Recommendation:** a teacher-facing "delete this student's attempts" action and an account/data deletion path; document a retention period (e.g. attempts auto-purged after the school year) and implement a purge job.

### G3 — Plaintext answers behind a weak gate — **Severity: High (compounds A2)**
Children's writing samples are stored in plaintext and retrievable via the brute-forceable history RPC. From a privacy standpoint this is a **personal-data breach waiting to happen**. The S2/A2 fix is also a privacy control. Consider whether storing full answer text is even necessary, or whether a mistake summary suffices (data minimization, Art. 5).

### G4 — No retention policy / unbounded accumulation — **Severity: Med**
Attempts, anonymous users, and audio accumulate forever. GDPR storage-limitation (Art. 5(1)(e)) wants a defined retention period. **Recommendation:** set retention (configurable per school), purge anonymous `auth.users` with no recent activity, and lifecycle-expire orphaned storage objects.

### G5 — Third-country / sub-processor transparency — **Severity: Med**
Data flows to **Google Cloud** (TTS, Vision OCR) and the platform runs on Supabase. These are sub-processors that must be disclosed and covered by DPAs/SCCs. Teacher content and (for OCR) potentially student handwriting images are sent to Google. **Recommendation:** maintain a sub-processor list, confirm EU data residency / SCCs, and disclose in the privacy notice. Note OCR images may contain student work or faces — treat as sensitive.

### G6 — No privacy notice, ToS, or cookie/consent surface — **Severity: Med**
There is no privacy policy or ToS in the app. The spec itself flags the copyright/ToS need (§8) and it's unimplemented. **Recommendation:** ship a privacy notice (plain-language + child-readable version), a ToS prohibiting copyrighted material with the 500-word limit as a backstop, and surface them at signup and on the student entry screen.

### G7 — Logging hygiene — **Severity: Low**
Confirm no PII (names, answers, PINs) lands in Edge Function `console.error` or client logs. `on_dictation_save` logs error messages; ensure they never echo `full_text`. The PIN-hash comment already notes intent to avoid plaintext logging — extend that discipline to answers/names.

## 4.3 Privacy priorities
1. Establish controller/processor model + DPA + privacy notice (G1, G6) — foundational, mostly non-code.
2. Build export/delete + retention purge (G2, G4) — required to honor rights requests.
3. Fix the weak gate on plaintext answers (G3, = S2) and minimize stored answer data.
4. Sub-processor disclosure + EU-residency confirmation (G5).

# Part 5 — UX / Accessibility & Learning-Design Review

> **Lens:** Can a 10-year-old on a phone, a teacher in a hurry, and a screen-reader user all succeed? Blends WCAG accessibility with pedagogy (this is a *learning* tool, not just an app).

## 5.1 Accessibility (WCAG) findings

### U1 — Sub-minimum, non-focusable controls — **Severity: Med**
The speed and pause selectors (`_SpeedRow`/`_PauseRow`) are `GestureDetector`-wrapped `Container`s: below the 44×44px target (WCAG 2.5.5), not keyboard-focusable, no semantic role, no selected-state announcement for screen readers. **Fix:** use `ChoiceChip`/`SegmentedButton` (focusable, labeled, ≥48px) — also less code.

### U2 — Color-only status encoding — **Severity: Med**
The results diff conveys correct/wrong/missing largely through color (green/red/amber) on tinted backgrounds. Fails WCAG 1.4.1 (use of color) for color-blind users and likely 1.4.3 contrast on the low-alpha fills. Wrong words use strikethrough (good — keep that as the non-color cue); add icons/labels for "missing," and audit contrast in **both** light and dark themes. There's a `darkTheme` wired up but the diff palette wasn't designed for it.

### U3 — Screen-reader narration of the player — **Severity: Med**
The player communicates state via a small grey text label (`_statusLabel`) and visual highlight. A non-sighted student gets no live announcement of "Sentence 3 of 8" or "Next sentence in 5 seconds." **Fix:** wrap status in a `Semantics`/`liveRegion` so transitions are announced; ensure the highlighted sentence is reachable by the screen reader.

### U4 — No captions / visual support during listen-only — **Severity: Low-Med**
A deaf or hard-of-hearing student can't use a pure-audio dictation at all. That's somewhat inherent to "dictation," but a teacher should at least be able to enable a partial-hint mode as an accommodation — the modes exist (`partial_hint`), so surface them as an accessibility setting, not just a practice toggle.

## 5.2 Usability findings

### U5 — Handing a dictation to 30 phones is clunky — **Severity: Med**
Typing a 6-char code on 30 devices is error-prone (and the hex alphabet includes easily-confused chars). **Fix:** QR code (= QW2) projected on the board; this is the single biggest classroom-flow win.

### U6 — Identity step friction & history discoverability — **Severity: Low-Med**
Returning students must re-type name + PIN per browser (SharedPreferences is per-device), and "See my past results" is a small text button below the fold of the identity panel. Combined with the brute-force risk (A2), the whole name+PIN identity model is the weakest UX *and* security link — real accounts (P3) fix both.

### U7 — Destructive actions lack confirmation/undo — **Severity: Low**
Dictation delete has no confirm/undo (per Part 1). For teachers who've spent time crafting content, an accidental delete is painful.

### U8 — Error/empty states are inconsistent — **Severity: Low**
Good shared widgets exist (`ErrorView`, `EmptyState`, `LoadingOverlay`) but the player uses bare `CircularProgressIndicator`s and generic strings. Standardize on the shared widgets for a coherent feel and better guidance ("Audio is still generating — check back in a moment" vs a spinner).

## 5.3 Learning-design findings

### U9 — Scoring model isn't pedagogically configurable — **Severity: Med (ties to P1)**
A single normalized "right/wrong" per sentence is blunt for language learning. Teachers will want: strict orthography (capitalization, umlaut, ß, punctuation — the real lesson) vs. lenient (content only, for beginners), and **partial credit** per word rather than all-or-nothing per sentence (the word-level diff already computes this — surface it in the score). This makes the tool usable across age groups.

### U10 — No feedback loop beyond the score — **Severity: Low**
After finishing, the student sees a diff but no next step ("practice the 3 words you missed," "try again at 0.75×"). A lightweight "retry missed sentences" action turns assessment into practice — cheap, and on-mission for a learning tool.

### U11 — Cognitive load of simultaneous listen + type — **Severity: Low**
The typing panel is always visible during listen-only mode, which can pull young students out of the "listen, then write" discipline real dictation teaches. Consider a teacher setting: type-after-each-sentence vs. type-at-end, matching classroom methodology.

## 5.4 UX priorities
1. QR/code sharing (U5) and confirm/undo (U7) — quick classroom wins.
2. Accessible controls + color-independent status (U1–U3) — before any wider rollout; cheapest to fix now.
3. Configurable, partial-credit, orthography-aware scoring (U9, = P1) — product-defining.
4. Real accounts to retire the name+PIN model (U6, = P3).

## Sprint 1 — Close the Trust Boundary *(~2 weeks, highest priority)*

**Goal:** Move scoring authority to the server. This single sprint closes the biggest security hole (A1/S1), eliminates score forgery (P2), removes the duplicated logic (C1), and delivers the headline product differentiation (P1/U9) — all as one coherent change.

### Tasks

**1.1 — Extract `lib/core/scoring/scoring.dart`**
- Refs: C1, P1, U9
- Pure Dart module with no Flutter/Supabase dependency.
- Exports:
  - `enum ScoringMode { strict, lenient }` — strict grades capitalization, ß/ss, punctuation; lenient normalizes before compare (current behavior)
  - `String normalizeStrict(String s)` — only lowercases, no punctuation strip
  - `String normalizeLenient(String s)` — current `_normalize` behavior kept as the default for lenient
  - `WordDiff diffWords(String student, String expected, ScoringMode)` — extracted from `student_results_view.dart`
  - `SentenceScore scoreSentence(String student, String expected, ScoringMode)` — returns `{isCorrect, wrongWords, missingWords, errorCategories}`
  - `AttemptScore scoreAttempt(List<DictationSentence> sentences, Map<int,String> answers, ScoringMode)` — aggregate
- **Done:** `player_screen.dart` and `student_results_view.dart` import and use this module; both `_normalize` duplicates deleted.
- **Done:** Unit tests cover at least: exact match, case mismatch, ß vs ss, missing umlaut, punctuation diff, blank answer, extra words.

**1.2 — Migration `008_submit_attempt_rpc.sql`**
- Refs: S1, S3, A1, A3, P2, G3
- `SECURITY DEFINER` function `submit_attempt(p_dictation_id uuid, p_answers jsonb, p_student_name text, p_pin_hash text, p_started_at timestamptz, p_scoring_mode text default 'lenient')`:
  1. Verifies `p_dictation_id` has a `share_code` (rejects attempts on private dictations).
  2. Loads `dictation_sentences` ordered by `position`.
  3. Scores server-side (mirrors `scoring.dart` logic in PL/pgSQL — lenient mode for now; strict mode as a named parameter for Phase 3).
  4. Inserts `attempts` row with computed `score`, `score_correct`, `score_total`, `answers`.
  5. Returns the inserted row as JSON.
- Drops the `attempts: insert own` direct-insert RLS path once the RPC is the sole insertion route (or tighten it to service_role only).
- **Done:** Direct `INSERT INTO attempts` from the client is blocked by RLS; all inserts go through the RPC.

**1.3 — Update `attempts_repository.dart`**
- Refs: C4, QW3, S1
- Replace `_client.from('attempts').insert(...)` with `_client.rpc('submit_attempt', params: {...})`.
- `saveAttempt` now `async` and returns `(Attempt?, AttemptFailure?)` — remove fire-and-forget.
- Reset `_savingAttempt` in the `finally` block.
- **Done:** Failed saves propagate to the caller.

**1.4 — Update `player_screen.dart` to await and report**
- Refs: QW3, C4
- `_saveAttempt` becomes `Future<void> _saveAttempt()`, awaited before `setState(() => _showResults = true)`.
- On failure: show a `SnackBar` with a "Retry" action that re-calls `_saveAttempt`.
- Remove the now-dead client-side score computation (delegated to RPC).
- **Done:** Student sees confirmation that results were saved; a failure is surfaced, not swallowed.

**1.5 — Add `ScoringMode` toggle to teacher create/edit screens**
- Refs: P1, U9
- New `scoring_mode text not null default 'lenient'` column on `dictations` (migration `008` also adds this).
- `DictationDifficulty`-style enum `ScoringMode` in Dart domain.
- Toggle in create/edit screen: "Lenient (content only)" vs "Strict (capitalization, ß, punctuation)".
- Player passes `dictation.scoringMode` into `scoreAttempt` and the RPC.
- **Done:** A German teacher sets strict mode; a student writing "der hund" for "Der Hund." is marked wrong; "Strasse" for "Straße" is marked wrong.

## Sprint 2 — Security Hardening *(~1 week)*

**Goal:** Close the remaining high/med severity attack paths before any marketing or school rollout.

### Tasks

**2.1 — Salt + server-side PIN hash (`get_student_attempts`)**
- Refs: S2, A2, G3
- Add `student_pin_salt text` column to `attempts`.
- Migration `009_salted_pin.sql`: update `get_student_attempts` to accept raw PIN (`p_pin text`), generate/store a per-row salt on insert (via `submit_attempt` RPC — done in Sprint 1), and verify with `encode(digest(p_pin_salt || p_pin, 'sha256'), 'hex')`.
- Remove the `p_pin_hash` parameter; client sends the raw PIN over TLS.
- Update `pin_hash.dart` and `attempts_repository.dart` accordingly.
- **Done:** Precomputing 10,000 SHA-256 hashes no longer defeats the gate; each row has a unique salt.

**2.2 — Rate-limit the history RPC**
- Refs: S2, A2
- Migration `009` also adds `pin_attempts(anon_uid uuid, attempted_at timestamptz)` table.
- `get_student_attempts` checks: if ≥10 attempts from `auth.uid()` in the last 15 minutes, raise `too_many_attempts`.
- Client surfaces this as "Too many attempts. Try again later."
- **Done:** Brute-force requires days instead of seconds.

**2.3 — Widen share-code alphabet**
- Refs: S4, A4
- Migration `010_wider_share_codes.sql`: replace `generate_share_code()` trigger with a version that draws from `BCDFGHJKMNPQRTVWXY2346789` (32 chars, no ambiguous O/0/I/1/L/5/S/Z) → 32⁶ ≈ 1.07B.
- Existing codes stay valid (lookup is still `upper(p_share_code)`).
- **Done:** New codes are unambiguous on classroom whiteboards and brute-force window jumps 64×.

**2.4 — Rate-limit `get_dictation_by_share_code`**
- Refs: S4, A4
- Supabase API gateway rate limit on the RPC endpoint, or a `code_lookups` counter table with a 429 response after N misses per IP/session per hour.
- **Done:** Sequential enumeration of the keyspace is no longer economically viable.

**2.5 — OCR image payload cap + rate limit**
- Refs: S5, A5
- `ocr_image/index.ts`: before calling Vision API, check `imageBase64.length > 7_000_000` (≈5 MB decoded) → return 413.
- Add per-user (`auth.uid()`) rate limit: max 20 OCR calls per hour (simple in-memory Deno state or a Supabase counter).
- **Done:** A single user can't drive unbounded Vision API spend.

**2.6 — TTS regeneration cooldown**
- Refs: S5, A5
- Add `last_tts_triggered_at timestamptz` column to `dictations` (migration `010`).
- `on_dictation_save`: if `now() - last_tts_triggered_at < 60 seconds` AND `full_text` hasn't changed, return 429. Update `last_tts_triggered_at` on each accepted run.
- **Done:** Edit-loop cost attack is blocked.
